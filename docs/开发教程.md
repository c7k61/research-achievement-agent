# 科研成果核验 Agent 开发教程

这份教程与仓库源码对应。按照下面的顺序亲自运行、阅读并修改代码，可以逐步理解一个包含工具调用的 Agent 原型。初始版本由 AI 辅助完成，项目的实际贡献可以通过自己的改动和验证逐步积累。

## 第一步 运行环境与样例

先在项目根目录打开 PowerShell，检查 Python 版本，需要 3.10 或以上。

```powershell
python --version
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e '.[documents]'
.\.venv\Scripts\python.exe demo.py
```

下面的命令都使用这个虚拟环境的 Python。macOS 或 Linux 可以将 `.\.venv\Scripts\python.exe` 换为 `.venv/bin/python`。

演示会导入两份虚构材料，显示论文已录用和专利申请已受理，并写入 `runs/demo.json`。打开 JSON，观察 `trace` 中检索、读取、核验的顺序。离线演示的工具规划由 `DemoModel` 确定。

如果暂时无法安装依赖，可以先运行 `python demo.py`。TXT 样例与核心流程只使用标准库。

## 第二步 文档解析与知识库

阅读 `research_agent/store.py` 中的 `read_pages` 和 `Store.ingest`。

`read_pages` 将文本、PDF 和 DOCX 转为文本页。PDF 保留原页码，DOCX 和文本文件使用全文定位。`ingest` 先解析目录中的全部材料，再在 SQLite 事务内替换当前数据，避免部分导入后知识库状态不完整。

```powershell
.\.venv\Scripts\python.exe -m research_agent ingest examples/materials
.\.venv\Scripts\python.exe -m research_agent list
```

练习时复制一份示例到 `private_materials`，修改成果名称后重新导入，再用 `list` 确认文件名、ID 和内容指纹。`ingest` 每次完整替换所指定数据库的材料集，练习数据可以使用独立数据库。

```powershell
.\.venv\Scripts\python.exe -m research_agent --db data/practice.sqlite3 ingest private_materials
```

## 第三步 理解检索

阅读 `tokens` 和 `Store.search`。中文按双字切分，英文按词切分。材料按 650 字分块，相邻块重叠 130 字。BM25 使用词频、文档频率和长度归一化计算相关性。

```powershell
.\.venv\Scripts\python.exe -m research_agent ask "专利目前是什么状态"
```

在生成的 `runs/latest.json` 中查看第一条 `search_evidence` 记录，比较 query、命中的片段和 score。可以分别输入“论文录用”“专利受理”，观察排名变化。

## 第四步 理解工具调用

阅读 `research_agent/agent.py` 中的 `TOOLS`、`Registry` 和 `run_agent`。

每个工具包含名称、描述和参数结构。`Registry` 验证工具名称和输入，只有本次已读取的材料才能进入成果核验。`run_agent` 将工具结果放回消息列表，再请求下一轮规划，直到模型返回成果 ID 或达到预算。

四个工具的职责分别是列出材料、检索片段、读取全文和核验成果。每次运行都有独立状态。最终成果 ID 必须来自本次核验结果，展示文本由程序根据核验字段生成。

练习时在测试文件中故意调用不存在的工具，观察错误会变成工具结果。阅读 `test_tool_errors_allow_recovery` 和 `test_budget_stops_infinite_tool_loop`，理解错误恢复与停止条件。

## 第五步 理解成果状态与引用

阅读 `research_agent/evidence.py`。字段模式根据成果类型、状态和证明类型作出结论，模板模式识别常见中文稿件录用通知、专利申请受理通知中的明确措辞。

将示例中的“状态：已录用”改为“状态：已发表”，保留“证明类型：稿件录用通知”，重新导入并运行。结果会提示材料不足。恢复样例后，再添加一个相反状态，结果会提示冲突。

查看 `citations` 中的 quote，回到对应材料逐字查找。引用可以检查结论来源，材料真实性仍需人工核对。

## 第六步 接入真实模型

从 [Ollama 官方网站](https://ollama.com/download) 安装并运行 Ollama，下载支持工具调用的模型。模型名称和下载体积以官方模型页面及本机配置为准。

```powershell
ollama pull qwen3:0.6b
.\.venv\Scripts\python.exe -m research_agent doctor --model qwen3:0.6b
.\.venv\Scripts\python.exe -m research_agent ask "核验论文和专利的状态" --mode ollama --model qwen3:0.6b --output runs/live-model.json
```

`doctor` 只检查服务和模型列表，不进行推理。确认 `service_reachable` 与 `model_available` 均为 true 后再问答。示例使用体积较小的模型便于初次联调，输出格式和工具选择的稳定性需要实际测试，可使用本机已经准备好的其他工具调用模型。

打开真实运行记录，确认 `mode` 为 `ollama`，检查模型实际选择的工具，以及成果状态是否与原文一致。接口模拟测试只验证消息协议，真实推理成功后才能将真实模型联调记录到项目成果中。

Ollama 会收到问题和所读取的材料，服务地址默认为本机。原型目前按单次问题运行，对话历史随本次运行结束。

## 第七步 自动测试与持续集成

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

测试覆盖状态、引用、导入回滚、Agent 预算和协议错误。可以先修改一个预期值观察失败，再恢复预期并修复代码。仓库的 GitHub Actions 会在推送和 Pull Request 时分别用 Python 3.10 与 3.12 执行测试及离线演示。

## 第八步 在 GitHub 记录自己的改进

发布后克隆仓库，创建自己的功能分支，围绕一项具体改进提交代码。例如扩展一种通知模板、为扫描件增加 OCR，或为真实模型建立问答评估集。

```powershell
git switch -c feature/notice-template
git add research_agent/evidence.py tests/test_notices.py
git commit -m "Support another notice template with regression tests"
git push -u origin feature/notice-template
```

每个提交说明解决了什么输入问题、修改后的输出和测试结果。面试演示时先展示实际运行，再解释自己修改过的代码与设计取舍。
